# ML-подход

Документ описывает целевые решения и их проверку. Численные результаты не
приводятся без эксперимента; PoC-замены отмечены явно.

## PII: очистка и остаточный риск

### Решение

До классификации формализованные PII (email, телефон, карта, паспорт) заменяются
типизированными плейсхолдерами внутри закрытого контура. Затем независимый
локальный detector ищет остаточные и контекстные PII. Внешний LLM здесь
неприемлем: исходный текст нельзя выводить из контура, а обработка входит в
быстрый путь.

### Baseline и целевое развитие

Реализация PoC — regex-правила и консервативная остаточная проверка:
любой `residual_pii_score > 0` ведёт к `HUMAN_REVIEW`. ML-модели в PoC нет
(`pii_model_version="none-poc"`); score является детерминированной заглушкой, а
не вероятностью. Карта, паспорт и другие высокочувствительные данные всегда
направляются оператору даже после замены.

Целевое развитие — правила плюс локально размещённая open-source NER-модель,
дообученная внутри компании.

### Данные и разметка

- Источник — исторические тикеты всех каналов.
- Разметка включает span, тип и чувствительность PII; редкие случаи дополняются
  синтетикой.
- Split временной; сообщения одного тикета не разделяются между выборками.
- Критический safety-срез размечается двумя аннотаторами.

### Eval, пороги и fallback

- Основная метрика — recall по каждому типу PII.
- Сквозная safety-метрика — доля тикетов с PII, оставшимся после очистки.
- Precision замен — guardrail от потери смысла.
- Пороги detector калибруются отдельно по типам в пользу recall.
- Любой сигнал выше порога, неопределённость или отказ detector означают
  `HUMAN_REVIEW`.
- Для допуска к пилоту требуется отсутствие известных пропусков
  высокочувствительных PII на выделенном safety-наборе. Это критерий допуска, а
  не заявленный результат.

## Определение рискованных обращений

### Решение

Платежи, доступ к аккаунту, security, legal и safety всегда направляются
оператору. В быстром пути сначала проверяются выбранная пользователем тема и
явные признаки риска в тексте. Срабатывание правила нельзя отменить последующей
моделью; retrieval и генерация для такого тикета не запускаются.

Правила выбраны из-за высокой цены пропуска, малой задержки и понятной причины
решения. Для текущей версии отдельная ML-модель не нужна.

### Baseline и целевое развитие

PoC использует список рискованных тем и небольшой словарь русскоязычных
признаков. Это может пропускать перефразирования и ошибочно направлять оператору
безопасные обращения.

Явные критические правила сохраняются и в целевой системе. Для неоднозначных
текстовых признаков следующим кандидатом служит внутренний классификатор
`TF-IDF + Logistic Regression`, обученный на исторических тикетах. Сначала он
работает параллельно правилам, не влияя на маршрут. Заменять им неоднозначные
правила можно только после подтверждения, что число пропусков риска не выросло,
а лишних направлений оператору стало меньше.

### Данные и проверка

- Используются исторические тикеты с итоговой категорией и эскалацией; примеры
  legal и safety дополнительно проверяют профильные специалисты.
- Проверочная выборка отделяется по времени, сообщения одного тикета не
  разделяются между выборками.
- Для правил считаются статистики на истории: пропущенные рискованные тикеты и
  безопасные тикеты, лишний раз направленные оператору. Отдельный постоянный
  набор критических примеров защищает от ошибок при изменении правил.
- Для будущего классификатора главная метрика — recall по каждой рискованной
  категории. Его неопределённость всегда означает `HUMAN_REVIEW`.
- Обнаруженный критический пропуск останавливает автоматизацию затронутой
  категории до исправления правил.

## Классификация темы

### Решение

Целевая модель `TF-IDF + Logistic Regression` получает очищенный текст и
возвращает top-3 темы с уверенностью. Она достаточно быстра для sync-пути и
обучается на внутренней истории; embeddings и LLM на этом этапе не оправданы по
задержке, стоимости и сложности.

Выбранная пользователем тема остаётся независимым сигналом и не подаётся в
модель, иначе проверка конфликта потеряет смысл. Рискованная тема в прогнозе
всегда означает `HUMAN_REVIEW`.

### Baseline и данные

Простейший baseline — выбранная пользователем тема. PoC использует
keyword-классификатор безопасных тем; его `confidence` задан вручную и не
является вероятностью. Целевая модель обучается на всех темах.

Целевая метка — итоговая основная тема, подтверждённая оператором. Исторические
метки выборочно проверяются, связанные сообщения и дубликаты массовых инцидентов
не разделяются между выборками. Train, validation и test отделяются по времени;
для редких тем применяются веса классов. Пилот ограничен `ru-RU`, остальные
языки до накопления данных направляются оператору.

### Качество, пороги и fallback

- Главная метрика — macro F1, чтобы частые темы не скрывали ошибки на редких;
  дополнительно проверяется recall каждой темы.
- Порог выбирается отдельно по темам после калибровки вероятностей: повышение
  порога снижает покрытие, но уменьшает ошибки среди принятых решений.
- Общая цель не более 2% ошибочных автозакрытий проверяется для всего
  конвейера, а не только для классификатора.
- `HUMAN_REVIEW` назначается при уверенности ниже порога, конфликте с выбранной
  темой, рискованном прогнозе, неподдерживаемом языке или отказе модели.
- Порог PoC `0.75` демонстрационный и не переносится в целевую систему без
  проверки на данных.

### Новые темы

`GENERAL` — отдельная тема для обращений вне справочника; низкая уверенность
означает отказ от решения, а не автоматическое присвоение `GENERAL`.

Для новой темы владелец справочника задаёт критерии, после чего похожие
исторические и новые тикеты размечаются вручную. Недорогая Logistic Regression
полностью переобучается на обновлённом справочнике. Новая версия сначала
сравнивается со старой без влияния на маршрут, затем помогает оператору и лишь
после накопления подтверждённых примеров допускается к автоматизации. Проверка
должна охватывать и новую, и старые темы. Низкоуверенные тикеты и `GENERAL`
служат источником кандидатов на дальнейшее расширение справочника.
