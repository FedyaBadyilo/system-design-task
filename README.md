# Автоматизация обработки тикетов — PoC

Локальный вертикальный срез AI-контура поддержки. Он принимает
валидированный mock-тикет, удаляет формализованные PII, оценивает тему, риск и
уверенность, ищет одобренную статью, формирует helpdesk payload либо передаёт
тикет оператору и сохраняет объяснимый audit trail в SQLite.

Быстрая классификация отделена от retrieval и генерации интерфейсами
`make_fast_decision()` и `process_generation_job()`. В PoC они вызываются
последовательно; в целевой архитектуре второй этап выполняется асинхронно.

## Локальный запуск

Требуется Python 3.11 или новее.

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install -e ".[dev]"
./.venv/bin/support-ai-demo --deterministic
./.venv/bin/python -m pytest
```

Demo показывает:

- безопасный happy path с `AUTO_REPLY_READY` и ссылкой на статью;
- платёжный тикет, который сразу получает `HUMAN_REVIEW`;
- low-confidence abstention;
- деградацию в `HUMAN_REVIEW` при недоступной генерации.

Для каждого примера CLI печатает входной mock-запрос, только фактически
выполненные этапы и краткий итог для helpdesk. JSON-контракты остаются внутри
приложения и тестов.

Собственный синтетический запрос можно передать отдельно:

```bash
./.venv/bin/support-ai-demo \
  --text "Не приходят уведомления, как их включить?" \
  --deterministic

./.venv/bin/support-ai-demo \
  --text "С карты дважды списали деньги" \
  --channel web \
  --selected-topic payments \
  --deterministic
```

SQLite создаётся в `.data/audit.db` и не попадает в Git.

## Реальный LLM

Скопируйте `.env.example` в `.env` и заполните:

```text
LLM_BASE_URL=https://polza.ai/api/v1
LLM_API_KEY=...
LLM_MODEL=provider/model-id
```

После этого happy path использует один OpenAI-compatible вызов:

```bash
./.venv/bin/support-ai-demo --scenario happy
```

Ключ не выводится и не сохраняется в audit. Во внешний LLM передаются только
очищенный текст и найденные фрагменты базы знаний. Невалидный ответ, timeout или
ошибка провайдера не подменяются успешным шаблоном: тикет передаётся оператору.

## Что реализовано, а что замокировано

Реально работают Pydantic-контракты, regex-очистка PII, policy, TF-IDF retrieval,
структурированная LLM-генерация, проверки ответа, идемпотентность и
нормализованный SQLite-аудит. Keyword-классификатор, локальная база знаний и
детерминированный генератор — явно обозначенные PoC-замены.

В целевой системе вместо них используются обученный и откалиброванный
`TF-IDF + Logistic Regression`, управляемая база знаний, локальный PII detector,
очередь и интеграция с helpdesk. UI, HTTP API и Docker намеренно не входят в
этот PoC. Подробнее: [архитектура](docs/architecture.md).

## Ограничения

- Тестовые статьи и keyword-правила не доказывают качество модели.
- Нагрузочные характеристики 200 тысяч тикетов в день проверены только
  архитектурно, а не этим локальным процессом.
- Ответ считается готовым к отправке, но PoC не отправляет и не закрывает тикет.
- Реальный провайдер может отвечать нестабильно; безопасный fallback проверен.
